# Security policy

## Статус

RAG Tender находится в Technical Preview. Публичная видимость исходников **не означает**, что настройки подходят для открытого production. Не направляйте реальные коммерческие тендеры или секреты на общедоступный экземпляр без согласованной модели доступа.

## Как сообщить об уязвимости

Предпочтительно отправить **private security advisory** через GitHub → Security → Advisories репозитория, если функция доступна. Не помещайте эксплуатационные детали, токены, данные клиентов или секреты в публичные issues и PR. Если private advisory недоступен, свяжитесь с владельцем репозитория через согласованный приватный канал.

## Минимальные меры перед деплоем

- Задайте уникальные `API_AUTH_TOKEN` (минимум 32 символа), `POSTGRES_PASSWORD`, `API_DATABASE_PASSWORD`, `OPENAI_API_KEY` и `DEEPSEEK_API_KEY` вне Git.
- Не делайте API/PostgreSQL/Qdrant публично доступными: Compose публикует API/Postgres на loopback. Для внешнего клиента обеспечьте TLS reverse proxy, network ACL и отдельную аутентификацию/авторизацию по требованиям среды.
- Ограничьте **расходы у провайдеров**: process-local admission не ограничивает токены или деньги.
- Проверьте журнал истории Git и git-lfs данные на секреты перед публикацией; используйте отдельный сканер (например, gitleaks) и GitHub secret scanning, если доступен.
- Перед изменением пароля уже существующей PostgreSQL обновите пароль роли **в самой БД**, а не только в `.env`.
- Делайте backup PostgreSQL, проверяйте restore и миграции на копии боевой БД.
- Учитывайте, что request/response history и диагностические логи могут хранить коммерчески чувствительные тендерные строки. Настройте retention и контроль доступа к PostgreSQL/Loki.
- Проверяйте право на распространение LD-каталога, Qdrant snapshot и сторонних источников, даже если технически они доступны в ветке.

Если секрет попал в Git, **перевыпустите его** у провайдера; простой коммит с удалением строки не удаляет его из истории.
